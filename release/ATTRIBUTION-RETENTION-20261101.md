## Supported click handoff

1. Proposed ad destination is the dedicated canonical `https://foodmyway.app/ad-measurement`, with TikTok's one `ttclid` query. No app/recipe/auth SPA loader. The only accepted query is exactly one `ttclid`, 1–1024 ASCII letters/digits/dot/underscore/hyphen; no hash, other fields, duplicate keys, unsafe origin/port or GPC/DNT. Capture accepts no referrer or exact HTTPS www.tiktok.com/m.tiktok.com/tiktok.com origins; referrer path/query is never saved or forwarded. The SDK document still requires an empty referrer. This bound/alphabet is a conservative application limit, NOT a claimed official TikTok specification. Invalid input is suppressed, not normalized or forwarded.
2. No identifier capture, cookie write, consent API request or SDK initialization occurs at import. Only an explicit Allow action parses the landing identifier and stores a native-expiring 15-minute pending cookie (bounded click ID, offer, fixed request ID and expiry only), then FULLY navigates to a NEW clean canonical document. History replacement is not sufficient to clear document.referrer. No consent API or SDK runs in the capture document. An incoming ad URL necessarily already reached the browser/hosting layer; this implementation cannot erase browser history/network/server logs or claim that those never saw the landing URL. It creates no pre-consent advertising storage or provider request.
3. Pending permission does not auto-grant or load the SDK. After the existing Kit email sign-in returns to the Kit, the visitor uses its noreferrer optional ad-choices link to the clean document and explicitly confirms before payment. This authenticated confirmation creates fresh server-time consent; the pending timestamp cannot backdate it. Signed-in consent immutably binds only the validated click ID to that actor, offer, policy and one-hour grant. Existing exclusions/reviewed start/revision requirements remain. An idempotent grant cannot swap the click. Another account cannot read or use the authenticated binding. Pending cookie state is untrusted same-browser input, not identity or ownership evidence. The click ID is not persisted in localStorage, event properties, Stripe metadata or Payment Links.
4. Every fresh SDK load makes bounded authenticated server preflight, checking current enablement, account, consent expiry/withdrawal and exclusions. Only this response supplies the SDK click binding. A known grant response clears only its matching pending request/click/offer cookie before SDK startup; a newer pending cookie is preserved and prevents SDK startup. The adapter places it in the first-party `ttclid` cookie scoped to `/ad-measurement`, Secure, SameSite=Lax, at most the remaining one-hour grant. A no-click grant clears this application's prior scoped cookie. The document must be clean and referrer-free before the script can be created. Unknown responses/timeouts retain uncertainty fences; no automatic retry.
5. The visitor follows the unchanged Kit/Founding route and Payment Link. On returning in the same browser/account within the grant, optional measurement checks the exact authenticated entitlement session/payment IDs against the signed webhook's `paid_orders`. No browser return, link click, consent grant or entitlement alone creates Purchase. Atomically reserved stable event ID and existing eligibility/refund/test checks remain authoritative. SDK queue acceptance is NOT delivery, attributed revenue or provider acceptance.
6. Withdrawal always deletes pending permission and the application's scoped click cookie, including a freshly reloaded page before SDK startup; it invokes/queues documented `revokeConsent` when SDK startup began, cancels pending load and retains the permanent dispatch fence. Already transmitted data cannot be recalled. Revocation does not claim deletion of all vendor cookies/data. Other tabs stop on their next validated load or local expiry; this is not an instantaneous cross-tab/vendor erasure guarantee.

New customers do not need a positive roster or pre-existing account. Signed-out capture, actual Kit sign-in/account creation and same-browser return are now tested using the real route code with synthetic transports; see SIGNEDOUT-ATTRIBUTION-20261101.md. Authenticated consent must still precede payment and exact ownership must match afterward. The cookie expires natively after 900 seconds even with the tab closed; its encoded JSON is bounded under 3000 characters, Secure, SameSite=Lax and scoped to /ad-measurement. Blocked/ambiguous cookie storage suppresses the handoff. Another browser/device, cleared cookies, expired permission, unsupported app referrer schemes, lost landing or a surviving nonempty referrer on the clean document remain unsupported. No automatic grant after login. Browser/email-app continuity and actual provider attribution remain unproven; no 100% attribution claim. A syntactically valid click ID is not proof of a genuine campaign click.

## Enforceable local redaction

The unapplied `0009_ad_measurement.sql` still creates exactly TWO tables. No parallel checkout, new account table, Events API or third-party credential.

- `ad_consents` holds the consent/click detail only until retention eligibility. After the database-clock 30-day boundary, the expired, unlinked grant is DELETED entirely after attempt redaction. No consent ID/redaction-time stub remains: the hashed payment event fence, not a consent history stub, prevents replay. The dormant redacted_at column is constrained to NULL for current read-path compatibility; new stubs are prohibited.
- `ad_purchase_attempts` becomes a permanent minimal tombstone: only SHA-256-derived `event_id` and `state` remain non-null. At 30 days since its detail creation OR its linked consent (whichever first), redaction erases session/consent/actor/revision/timing detail. Uncertain remains uncertain forever. The tombstone prevents duplicate events beyond TikTok's 48-hour window and after fresh grants, reused requests, cookie loss and SQLite reopen.
- `functions/_shared/ad-retention.mjs` performs an ACTUAL atomic two-update batch using SQLite's current clock, not a caller-selected cutoff. SQL rejects early/linked grant deletion, partial detail erasure, attempt restoration/reopening/deletion and NULL-based guard bypass. BEFORE INSERT guards also stop `INSERT OR REPLACE` from silently deleting/replacing an existing consent or event/session/consent fence. No cleanup HTTP endpoint exists. No request/payment path calls the helper.
